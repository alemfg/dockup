## 1. Before You Start

### What you are installing

ARBX is a **distributed system** made of multiple cooperating processes:

```
┌─────────────────────────────────────────────────────────────────┐
│                        ARBX System                              │
│                                                                 │
│  Brain (1 instance)     Workers (1+ per exchange)              │
│  ┌──────────────┐       ┌──────────┐  ┌──────────┐            │
│  │  Analysis    │◄──────│ Binance  │  │  Kraken  │  ...       │
│  │  Strategies  │  Redis│  Worker  │  │  Worker  │            │
│  │  Fleet Mon.  │Streams└──────────┘  └──────────┘            │
│  │  API :8000   │                                              │
│  └──────────────┘       ┌──────────┐  ┌──────────┐            │
│                          │ Uniswap  │  │  Forex   │            │
│  Infrastructure           │  Worker  │  │  Worker  │            │
│  ┌──────┐ ┌──────┐       └──────────┘  └──────────┘            │
│  │Redis │ │ PG   │                                              │
│  └──────┘ └──────┘       Worker Manager (1 per machine)        │
└─────────────────────────────────────────────────────────────────┘
```

> 📊 **Architecture diagram:** See the full interactive deployment map in your FigJam board or refer to `docs/SYSTEM_DESCRIPTION.md`.

The simplest setup runs everything on one machine via Docker Compose. A production setup distributes workers across multiple machines or cloud VMs.

### Read this first

- **Dry-run is always on by default.** No real trades execute until you explicitly set `dry_run: false`.
- **You do not need API keys to start.** All collectors simulate realistic prices if keys are absent.
- **Redis is required.** It is the nervous system — without it, nothing communicates.
- **PostgreSQL is optional for dry-run.** Disable it in config if you want a minimal start.

## 3. Installation — Quick Path (Docker)

This gets ARBX fully running in under 5 minutes with zero manual configuration.

> 📊 **Flow diagram:** Install steps — see the installation flowchart generated by the setup wizard above.

### Step 1 — Get the code

```bash
# Option A: from ZIP (if you received the project as a file)
unzip arbx-v4.4.zip
cd arbx

# Option B: from GitHub
git clone https://github.com/your-org/arbx.git
cd arbx
```

### Step 2 — Create your environment file

```bash
cp config/.env.example config/.env
```

For a first run, you only need to open `.env` and set one value:

```bash
nano config/.env
# Change: POSTGRES_PASSWORD=arbitrage_secret
# Change to something secure, e.g.: POSTGRES_PASSWORD=MyStr0ngP@ssword2026
```

Everything else can stay as default. Exchange API keys are optional — without them, ARBX simulates realistic prices.

### Step 3 — Start everything

```bash
make docker-up
```

This single command:
- Builds the brain image
- Builds the worker image
- Builds the frontend image
- Starts Redis, PostgreSQL, brain, three workers (Binance, Kraken, Uniswap), worker manager, Prometheus, and Grafana
- Waits for health checks to pass

Expected output after ~60 seconds:

```
✅ ARBX v4.4 started:

   Dashboard      → http://localhost:3000
   API            → http://localhost:8000
   API Docs       → http://localhost:8000/docs
   Prometheus     → http://localhost:9091
   Grafana        → http://localhost:3001  (admin / admin)

Workers running: binance · kraken · uniswap
```

### Step 4 — Verify it works

```bash
# Check all containers are healthy
docker compose -f docker/docker-compose.yml ps

# Check brain API responds
curl http://localhost:8000/api/health
# Expected: {"status":"ok"}

# Check workers connected
curl http://localhost:8000/api/fleet/workers | python3 -m json.tool
# Expected: list of 3 workers with status "healthy"
```

Open `http://localhost:3000` — the dashboard should show 3 workers in the Fleet Health tab, and prices populating in the Market Feed tab within 10–15 seconds.

### Stopping everything

```bash
make docker-down
# or: docker compose -f docker/docker-compose.yml down
```

Data is preserved in Docker volumes. To destroy all data:

```bash
docker compose -f docker/docker-compose.yml down -v
```

## 4. Installation — Local Development

Use this path if you want to edit the code while it runs, or if you cannot use Docker.

### Step 1 — Create Python virtual environment

```bash
cd arbx

python3 -m venv .venv
source .venv/bin/activate          # Linux / macOS
# .venv\Scripts\activate           # Windows PowerShell

pip install -r requirements.txt
pip install pytest pytest-asyncio pytz black    # dev extras
```

### Step 2 — Start Redis (required)

```bash
# Fastest: Docker for just Redis
docker run -d --name arbx-redis -p 6379:6379 redis:7-alpine

# Verify it runs
redis-cli ping        # Should return: PONG
```

### Step 3 — Start PostgreSQL (optional)

```bash
# Docker for just Postgres
docker run -d --name arbx-postgres \
  -e POSTGRES_DB=arbitrage \
  -e POSTGRES_USER=arbitrage \
  -e POSTGRES_PASSWORD=arbitrage_secret \
  -p 5432:5432 postgres:16-alpine

# Or disable postgres entirely in config/config.yaml:
# postgres:
#   enabled: false
```

### Step 4 — Configure environment

```bash
cp config/.env.example config/.env
# Edit config/.env with your values
```

### Step 5 — Start the brain (Terminal 1)

```bash
source .venv/bin/activate
make brain
# or: python -m scripts.run_brain
```

Watch for this line — it means the brain is ready:

```
MessageBus connected to Redis localhost:6379
```

### Step 6 — Start a worker (Terminal 2)

```bash
source .venv/bin/activate

# Binance worker with simulated prices (no API keys needed)
EXCHANGE=binance PAIRS=BTC/USDT,ETH/USDT,SOL/USDT make worker

# Kraken worker
EXCHANGE=kraken PAIRS=BTC/USDT,ETH/USDT make worker
```

Within 5 seconds of starting a worker, the brain's fleet log should show:

```
[FLEET] New worker registered: worker-binance-xxxxx (binance)
```

### Step 7 — Start the frontend (Terminal 3)

```bash
cd frontend
npm install
npm run dev
# Dashboard at http://localhost:5173
```

### Step 8 — Run tests

```bash
source .venv/bin/activate
make test
# Expected: 18 passed
```

## 5. Configuration Deep Dive

All configuration lives in two files:

| File | Purpose |
|---|---|
| `config/config.yaml` | Application settings — strategies, analysis, trading parameters |
| `config/.env` | Secrets — passwords, API keys, webhook URLs |

**The rule:** Nothing secret goes in `config.yaml`. Nothing structural goes in `.env`.

### 5.1 Critical settings in config.yaml

```yaml
brain:
  dry_run: true           # ← ALWAYS start with true
  log_level: INFO         # DEBUG for troubleshooting, INFO for normal ops

trading:
  min_profit_percent: 0.5  # Minimum spread to consider (after fees)
  max_position_usd: 10000  # Hard cap per trade simulation
  default_volume: 0.5      # Volume in base asset for simulations

analysis:
  cr_9am:
    enabled: true
    timezone: "America/New_York"   # ← Match your trading session
    pairs:
      - "BTC/USDT"
      - "ETH/USDT"
```

### 5.2 Enabling real exchange data

Without API keys, all workers simulate prices. To enable real data:

```bash
# In config/.env:
BINANCE_API_KEY=your_actual_key_here
BINANCE_API_SECRET=your_actual_secret_here
```

Then restart the worker. It will automatically detect the keys and switch from simulation to live CCXT.

**Recommended API key permissions** (read-only is safest for research):
- ✅ Read market data (tickers, orderbooks)
- ✅ Read account balances
- ❌ No spot trading permission until you explicitly enable live mode
- ❌ No withdrawal permission — never

### 5.3 Enabling blockchain / DEX data

```bash
# In config/.env:
WEB3_PROVIDER_URL=https://mainnet.infura.io/v3/YOUR_PROJECT_ID
```

Get a free Infura key at `infura.io` — the free tier (100,000 requests/day) is sufficient for research.

### 5.4 Configuring alerts

```yaml
# config/config.yaml
alerts:
  console: true          # Always on

  ntfy_enabled: true     # Push to your phone (free)
  ntfy_topic: "arbx-my-alerts"    # Visit ntfy.sh to set up

  slack_enabled: true
  slack_webhook: "${SLACK_WEBHOOK_URL}"   # Set in .env

  email_enabled: false   # Requires SMTP config
```

**Setting up ntfy (simplest alert):**
1. Install the ntfy app on your phone (iOS or Android)
2. Subscribe to your topic name
3. Set `ntfy_topic` in config to the same topic name
4. Done — alerts arrive on your phone within seconds

### 5.5 Tuning analysis plugins

Turn plugins on/off per-pair without writing code:

```yaml
analysis:
  plugins:
    rsi:
      enabled: true
      weight: 0.15
      params:
        period: 14            # Default RSI period

  # Disable ARIMA for meme coins (too volatile for prediction)
  pairs:
    "DOGE/USDT":
      plugins:
        arima_predictor: { enabled: false }
        sentiment: { enabled: true, weight: 0.30 }

  # Add gas awareness for Uniswap (not relevant for CEX)
  exchanges:
    uniswap:
      plugins:
        arima_predictor: { enabled: false }  # DEX prices too noisy
```

## 6. Deployment Architecture

### Single-machine (development / small scale)

All services on one machine via Docker Compose. Suitable for research, backtesting, and learning the system.

```
One Machine
├── arb-brain          (CPU-bound: analysis, strategies)
├── arb-redis          (I/O: message bus)
├── arb-postgres       (I/O: persistence)
├── arb-worker-binance (network-bound: exchange API)
├── arb-worker-kraken  (network-bound: exchange API)
├── arb-worker-uniswap (network-bound: RPC calls)
├── arb-worker-manager (daemon: spawns containers)
├── arb-frontend       (static: nginx)
├── arb-prometheus     (scraper)
└── arb-grafana        (dashboards)
```

**Start:** `make docker-up`

### Multi-machine (production)

> 📊 **Diagram:** See the deployment architecture FigJam diagram above for a visual map of this layout.

Distribute load for lower latency and IP diversity:

```
Brain Server (1x)                    Worker Servers (2x+)
├── arb-brain                        ├── worker-binance-01 (Machine B)
├── arb-redis          ◄────────────► ├── worker-kraken-01  (Machine B)
├── arb-postgres                     ├── worker-uniswap-01 (Machine B)
├── arb-worker-manager               └── arb-worker-manager
├── arb-prometheus
├── arb-grafana                      Failover Server (1x standby)
└── arb-frontend                     ├── arb-worker-manager (ready)
                                     └── (spawns when brain requests)
```

**Redis networking:** Workers on remote machines need to reach Redis. In production, secure this with:

```bash
# Option A: SSH tunnel (simplest and secure)
ssh -L 6379:localhost:6379 user@brain-server &
# Now Redis is accessible at localhost:6379 on the worker machine

# Option B: Redis with password + TLS (production)
# Add to redis.conf on brain server:
# requirepass your_redis_password
# tls-port 6380

# Option C: VPN (most secure, recommended for production)
# Use WireGuard or OpenVPN between machines
```

### Cloud deployment (AWS / GCP / Digital Ocean)

**Brain server:** 2–4 vCPU, 4–8 GB RAM VM  
**Worker servers:** 1–2 vCPU, 1–2 GB RAM VM each  
**Redis:** Managed Redis (AWS ElastiCache, GCP Memorystore, or self-hosted on brain server)  
**PostgreSQL:** Managed PostgreSQL (AWS RDS, GCP Cloud SQL, or self-hosted)

**Recommended VMs per cloud:**

| Cloud | Brain | Workers |
|---|---|---|
| AWS | t3.medium | t3.small |
| GCP | e2-medium | e2-small |
| DigitalOcean | 2GB Droplet | 1GB Droplet |
| Hetzner | CX21 | CX11 |

**Sample Docker Compose override for cloud:**

```yaml
# docker/docker-compose.cloud.yml (override file)
services:
  brain:
    environment:
      REDIS_HOST: your-managed-redis.cache.amazonaws.com
      POSTGRES_HOST: your-managed-pg.rds.amazonaws.com
```

```bash
docker compose \
  -f docker/docker-compose.yml \
  -f docker/docker-compose.cloud.yml \
  up -d
```

## 7. Deploying Workers on Remote Machines

Workers can run anywhere with network access to Redis. This section walks through deploying a worker on a second machine.

### 7.1 Prepare the remote machine

```bash
# SSH into the remote machine
ssh user@remote-machine

# Install Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker

# Pull the worker image
# Option A: build from source
git clone https://github.com/your-org/arbx.git
cd arbx
docker build -f Dockerfile.worker -t arbitrage-worker:v4.4 .

# Option B: pull from your registry (if you pushed the image)
docker pull your-registry/arbitrage-worker:v4.4
```

### 7.2 Generate worker credentials

Run this on the **brain machine**:

```bash
python scripts/generate_worker.py \
    --id worker-binance-remote-01 \
    --exchange binance \
    --pairs BTC/USDT ETH/USDT SOL/USDT \
    --expires 30

# This creates: worker-binance-remote-01.env.secret
```

### 7.3 Transfer credentials securely

```bash
# Secure transfer (never email or Slack these)
scp worker-binance-remote-01.env.secret user@remote-machine:/opt/arbx/

# Delete local copy after transfer
shred -u worker-binance-remote-01.env.secret    # Linux
# rm -P worker-binance-remote-01.env.secret     # macOS
```

### 7.4 Register the worker with the brain

```bash
# On the brain machine — register so brain accepts messages from this worker
curl -X POST http://localhost:8000/api/security/workers/register \
  -H "Content-Type: application/json" \
  -d '{
    "worker_id": "worker-binance-remote-01",
    "exchange": "binance",
    "allowed_pairs": ["BTC/USDT", "ETH/USDT", "SOL/USDT"],
    "can_execute_orders": false,
    "expires_days": 30
  }'

# Save the secret_key from the response — add it to the .env.secret file
# WORKER_SECRET_KEY=<value from response>
```

### 7.5 Start the worker on the remote machine

```bash
# SSH into remote machine
ssh user@remote-machine

docker run -d \
  --name worker-binance-remote-01 \
  --restart unless-stopped \
  --memory 256m \
  --cpus 0.5 \
  --env-file /opt/arbx/worker-binance-remote-01.env.secret \
  -e REDIS_HOST=brain-server-ip \
  -e MACHINE_ID=remote-nyc \
  -e TICK_INTERVAL_MS=1500 \
  arbitrage-worker:v4.4
```

### 7.6 Verify the worker connected

```bash
# On brain machine — check fleet
curl http://localhost:8000/api/fleet/workers | python3 -m json.tool

# Look for: "worker_id": "worker-binance-remote-01", "status": "healthy"
```

Or check the dashboard → Fleet Health tab. The new worker should appear within 10 seconds.

### 7.7 Deploy the Worker Manager (for automatic failover)

The Worker Manager daemon on the remote machine enables the brain to spawn new workers there automatically when needed.

```bash
# On remote machine:
docker run -d \
  --name arbx-worker-manager \
  --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e REDIS_HOST=brain-server-ip \
  -e MACHINE_IP=remote-nyc-ip \
  -e MAX_WORKERS=5 \
  -e WORKER_IMAGE=arbitrage-worker:v4.4 \
  arbitrage-brain:v4.4 \
  python -m scripts.run_worker_manager
```

Once this is running, the brain can automatically start replacement workers on this machine when a worker on another machine fails.

## 8. Worker Registration & Security

### 8.1 How authentication works

Every message from a worker to the brain is authenticated with a cryptographic signature. The brain maintains a registry of known workers. Messages from unknown or revoked workers are rejected and logged.

```
Worker sends:
  {
    "payload": { "worker_id": "...", "price": 65000, "timestamp": 1234567890, "nonce": "uuid" },
    "signature": "hmac_sha256_of_payload_using_worker_secret_key"
  }

Brain verifies:
  1. worker_id exists in registry ✓
  2. worker is not revoked ✓
  3. timestamp within 30 seconds ✓
  4. nonce not seen before ✓
  5. signature matches stored secret key ✓
  → Accept message
```

### 8.2 Register a new worker

```bash
curl -X POST http://localhost:8000/api/security/workers/register \
  -H "Content-Type: application/json" \
  -d '{
    "worker_id": "worker-kraken-02",
    "exchange": "kraken",
    "allowed_pairs": ["BTC/USDT", "ETH/USDT"],
    "can_execute_orders": false,
    "max_order_size_usd": 0,
    "ip_whitelist": [],
    "expires_days": 30
  }'
```

**Response:**
```json
{
  "worker_id": "worker-kraken-02",
  "secret_key": "a3f8b2c1d4e5f6a7...",
  "message": "Store this secret key securely — it will not be shown again."
}
```

**Important:** Copy the `secret_key` immediately. It is shown once and never stored in plain text.

### 8.3 Revoke a compromised worker

```bash
# Via API (also sends kill command to the worker process)
curl -X POST http://localhost:8000/api/security/workers/worker-kraken-02/revoke

# Via dashboard: Security tab → [Revoke] button next to the worker
```

Revocation takes effect immediately — the next message from that worker will be rejected.

### 8.4 View the security panel

Open dashboard → Security tab to see:
- All registered workers with expiry dates
- Active / revoked status
- Recent rejected connection attempts (with IP addresses and reason)

## 9. Fleet Health & Automatic Failover

> 📊 **Diagram:** See the Fleet Failover State Machine diagram above for a visual map of all states and transitions.

### 9.1 What the brain monitors

Every 5 seconds, the fleet monitor evaluates every worker:

| Signal | Source | Threshold |
|---|---|---|
| Heartbeat presence | Heartbeat TTL | >15 seconds missing → DEAD |
| Error type | Heartbeat `last_error` | Classified against known patterns |
| Data freshness | Per-pair tick timestamps | >30 seconds no ticks → STALE |
| CPU usage | Heartbeat `cpu_pct` | >85% → OVERLOADED |
| Memory usage | Heartbeat `memory_mb` | >800 MB → OVERLOADED |
| API latency | Heartbeat `latency_ms` | >2000ms → advisory |

### 9.2 Automatic responses

| Condition detected | Action | Time to recovery |
|---|---|---|
| IP blocked (403/418) | Spawn replacement on different machine | ~9 seconds |
| Rate limited (429) | Spawn companion, split pairs | ~9 seconds |
| Worker crashed | Respawn on different machine | ~20 seconds |
| Worker overloaded | Spawn companion, split pairs | ~10 seconds |
| Data stale | Spawn parallel probe | ~35 seconds |
| High latency | Log advisory, suggest relocation | No auto-action |

### 9.3 Pair splitting

When a companion worker is spawned to share load, the brain reassigns pairs intelligently — highest-volume pairs stay on the most stable worker:

```
Original worker (overloaded): BTC/USDT, ETH/USDT, SOL/USDT, BNB/USDT
                                   ↓ brain reassigns
Original keeps:  BTC/USDT, ETH/USDT     (highest volume)
Companion gets:  SOL/USDT, BNB/USDT     (lower volume)
```

### 9.4 Manual fleet operations

```bash
# Kill a specific worker
curl -X POST http://localhost:8000/api/fleet/workers/worker-binance-01/kill

# Restart a worker (spawns replacement)
curl -X POST http://localhost:8000/api/fleet/workers/worker-binance-01/restart

# Manually spawn a new worker on a specific exchange
curl -X POST http://localhost:8000/api/workers/spawn \
  -H "Content-Type: application/json" \
  -d '{"exchange": "bybit", "pairs": ["BTC/USDT", "ETH/USDT"]}'

# Reassign pairs to a worker
curl -X POST http://localhost:8000/api/workers/worker-binance-01/reassign \
  -H "Content-Type: application/json" \
  -d '["BTC/USDT", "ETH/USDT"]'
```

## 11. Maintenance Routines

### Daily (automated — no manual action needed)

- Heartbeat monitoring: continuous
- Worker failover: automatic
- Opportunity deduplication: Redis TTL handles this
- Log rotation: Docker handles this automatically

### Weekly

```bash
# Check Redis memory usage
docker exec arb-redis redis-cli INFO memory | grep used_memory_human

# Check PostgreSQL database size
docker exec arb-postgres psql -U arbitrage -c "\l+"

# Review security rejection log
curl http://localhost:8000/api/security/workers | python3 -m json.tool | grep rejections
```

## 12. Backup & Recovery

### What needs backing up

| Data | Location | Criticality | Backup frequency |
|---|---|---|---|
| PostgreSQL database | Docker volume `postgres_data` | High | Daily |
| `config/.env` | Local file | Critical | Every change |
| `config/config.yaml` | Local file | High | Every change |
| Worker `.env.secret` files | Deployed machines | Critical | Store securely at creation |
| `config/certs/` | Local directory | Critical (production) | Every change |

### Backup commands

```bash
# PostgreSQL backup
docker exec arb-postgres pg_dump -U arbitrage arbitrage > backup_$(date +%Y%m%d).sql

# Redis snapshot (Redis auto-saves to volume — force a save now)
docker exec arb-redis redis-cli BGSAVE

# Config backup
tar -czf config_backup_$(date +%Y%m%d).tar.gz config/
```

### Recovery from backup

```bash
# Restore PostgreSQL
docker exec -i arb-postgres psql -U arbitrage arbitrage < backup_20260314.sql

# Restore config
tar -xzf config_backup_20260314.tar.gz
```

### Disaster recovery (full rebuild)

```bash
# 1. Start fresh
git clone https://github.com/your-org/arbx.git
cd arbx

# 2. Restore config
cp /path/to/backup/config/.env config/.env
cp /path/to/backup/config/config.yaml config/config.yaml

# 3. Start infrastructure
docker compose -f docker/docker-compose.yml up -d redis postgres

# 4. Restore database
docker exec -i arb-postgres psql -U arbitrage arbitrage < backup.sql

# 5. Start everything
make docker-up

# 6. Re-register workers (credentials need to be re-issued)
python scripts/generate_worker.py --id worker-binance-01 --exchange binance --pairs BTC/USDT ETH/USDT
```

## 13. Upgrading ARBX

### Minor version upgrade (e.g., 2.0.0 → 2.1.0)

```bash
# Pull latest code
git pull origin main

# Rebuild images with new code
docker compose -f docker/docker-compose.yml build

# Restart services (brief downtime)
docker compose -f docker/docker-compose.yml up -d

# Verify
curl http://localhost:8000/api/health
make test
```

### Major version upgrade

1. Read the release notes (`docs/V1_TO_V2_RELEASE_NOTES.md`)
2. Back up database and config
3. Follow the migration guide in the release notes
4. Test in dry-run mode before re-enabling any live features

### Rolling upgrade (zero downtime for workers)

Workers can be upgraded one at a time while the brain continues running:

```bash
# Build new worker image
docker build -f Dockerfile.worker -t arbitrage-worker:v4.4.1 .

# Update workers one by one
docker stop arb-worker-binance
docker rm arb-worker-binance
# Start new version
docker run -d --name arb-worker-binance \
  [... same env vars ...] \
  arbitrage-worker:v4.4.1

# Brain auto-detects the new worker via its heartbeat
```

## 14. Troubleshooting Reference

### Brain won't start

**Symptom:** `RuntimeError: MessageBus not connected`

```bash
# Check Redis is running
docker ps | grep redis
redis-cli ping          # Should return: PONG

# Check Redis host in config
grep REDIS_HOST config/.env
# Ensure it matches where Redis is actually running
```

**Symptom:** Brain starts but immediately exits

```bash
# Check logs for the actual error
docker compose -f docker/docker-compose.yml logs brain | tail -50
```

### Worker not appearing in fleet

```bash
# Step 1: Is the worker running?
docker ps | grep worker-binance

# Step 2: Can it reach Redis?
docker exec arb-worker-binance redis-cli -h $REDIS_HOST ping

# Step 3: Is it authenticated? Check brain logs
docker logs arb-brain | grep "REJECTED\|registered"

# Step 4: Network issue? Try from worker machine
nc -zv brain-server-ip 6379    # Should say: Connection succeeded
```

### No prices in dashboard

The dashboard needs:
1. Brain running → `curl localhost:8000/api/health`
2. At least one worker healthy → Fleet Health tab
3. 15–30 seconds after first worker connects for prices to populate

```bash
# Check market state directly
curl http://localhost:8000/api/market/prices | python3 -m json.tool
```

### CR signals not appearing

The CR plugin is time-gated: **only active 9:00–10:00 AM New York time.**

```bash
# Check current NY time
TZ="America/New_York" date

# Check if pair is configured
grep -A5 "cr_9am" config/config.yaml | grep pairs -A10
```

### High memory usage

```bash
# Check which container is using memory
docker stats --no-stream

# Brain high memory = too many analysis contexts
# Reduce by limiting PAIRS on workers
# Or increase available RAM on brain server

# Redis high memory = too many stream messages
docker exec arb-redis redis-cli INFO memory
docker exec arb-redis redis-cli XLEN stream:prices  # should be < 10000
```

### Worker IP blocked

If a worker's exchange blocks its IP (ARBX detects this automatically within 5 seconds), it:
1. Sets condition to `ip_block`
2. Reports in next heartbeat
3. Brain spawns replacement on different machine (if Worker Manager is running there)
4. Sends alert via configured channels

If automatic failover doesn't trigger (no Worker Manager on another machine), manually spawn:

```bash
curl -X POST http://localhost:8000/api/workers/spawn \
  -H "Content-Type: application/json" \
  -d '{"exchange": "binance", "pairs": ["BTC/USDT", "ETH/USDT"], "avoid_machine": "blocked-machine-ip"}'
```
